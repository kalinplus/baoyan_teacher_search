# Task0 Step2 规则驱动抓取方案

## 1. 问题定义
不同学校/学院的教师列表页面结构差异很大，常见差异包括：
- 人名区域与导航区域混杂
- 分页方式不同（下一页、页码、参数翻页）
- 列表可能在二级页面
- 部分页面为滚动加载或脚本渲染

因此，Step2 不能依赖单一通用正则，需要采用“规则驱动 + 站点适配器”的方式逐页打通。

## 2. 目标
- 输入：学校 + 学院 + 列表 URL
- 输出：`output/teacher_pool/{学校}/{学院}/teachers.json`
- 质量目标：
  - `teachers` 非空
  - 无重复
  - 不包含明显导航词、分页词、栏目词

## 3. 总体方案

### 3.1 抓取层（通用）
- 负责请求页面、编码处理、分页遍历、输出落盘。
- 默认使用 `requests` 抓取 HTML。
- 该层不负责判断“哪些文字是姓名”。

### 3.2 提取层（按站点规则）
- 每个学院页面对应一组提取规则（适配器）。
- 规则只描述“从哪里取名字”，例如：
  - 目标容器特征（class/id/模块标题）
  - 目标节点模式（如 `a` 标签文本）
  - 分页入口规则（next 链接、页码链接）
- 提取结果进入统一清洗流程。

### 3.3 清洗层（通用）
- 去空、去重、长度过滤（中文 2-4 字为主）
- 黑名单过滤（如：首页、上页、下页、尾页、学院、通知）
- 保持失败显式：抽取为空时直接报错，不静默降级。

### 3.4 验证层（通用）
- 自动校验：非空 + 去重
- 人工抽样：每个学院至少抽样 10 条人工确认
- 若误提取明显（导航词较多），视为失败，不写入“通过”结论。

## 4. 不依赖外部 API 的结论
这部分可以不使用外部 API：
- 第一阶段直接基于学院官网页面抓取（HTTP + 规则提取）即可。
- 仅当页面必须执行前端脚本才能拿到数据时，再评估引入浏览器渲染方案。
- 若需要新增依赖（例如浏览器自动化），先审批再落地。

## 5. 实施计划（可执行）

### Milestone A: 规则框架落地
- 改造 `src/teacher_list_collector.py`，支持“按页面规则提取”。
- 先内置少量规则，不引入新依赖。
- 输出维持现有契约不变。

验收：
- 至少 1 个学院页面准确提取并通过非空/去重校验。

### Milestone B: 分页与二级页支持
- 增加“下一页/页码”遍历。
- 增加“列表页 -> 详情页”模式（仅当人名在详情页时启用）。

验收：
- 至少 3 个学院页面稳定通过。

### Milestone C: 学院规则扩展
- 你提供页面结构描述，我按模板新增规则。
- 每新增一个学院，附带一条运行记录和抽样结果。

验收：
- 当前任务列表里的页面逐个打通，失败页面给出可复现原因。

### Milestone D: 结果质量门禁
- 增加轻量质量检查（黑名单命中率、疑似非姓名比例）。
- 质量不达标直接失败，避免“看似成功”的脏数据流入任务1。

验收：
- 不再出现大规模导航词混入 `teachers`。

## 6. 协作输入模板（你提供，我实现）
每个学院请提供以下信息：
1. 学校
2. 学院
3. 列表页 URL
4. 分页类型（无/下一页/页码/滚动加载）
5. 人名区域说明（模块标题、class/id 或可定位特征）
6. 该页可确认的 5-10 个姓名样本
7. 是否需要登录、验证码或特殊请求头

建议格式：

```md
学校：北京大学
学院：计算机学院 & 王选计算机研究所
URL：https://cs.pku.edu.cn/szdw/jyxl/amz/ALL.htm
分页类型：页码
人名区域：列表区域 class=...，姓名在 a 标签文本
姓名样本：张三、李四、王五...
限制：无登录，无验证码
```

## 7. 风险与边界
- 对脚本渲染站点，纯 requests 可能拿不到完整数据。
- 对强反爬站点，可能出现 403/验证码，需要单独策略。
- 本阶段优先“准确性与可复现”，不追求一次覆盖所有学校。
